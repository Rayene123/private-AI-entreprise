# Document Storage Architecture

## Storage architecture

```text
FastAPI
  ↓
Authentication
  ↓
RBAC
  ↓
Document-level authorization
  ↓
StorageService
  ↓
Private Supabase Storage
```

FastAPI is the application authorization boundary. `StorageService` is a thin integration adapter and does not make authorization decisions.

## Bucket

Document files are stored in the private Supabase Storage bucket `enterprise-documents`. The bucket is not public, and the backend uses the service-role Supabase client only after authorization has succeeded. Clients do not receive public object URLs or direct bucket access.

The migration protects the bucket with restrictive `storage.objects` policies as defense in depth. These policies are not a replacement for backend authorization.

## Storage path

Objects use this structure:

```text
documents/{document_id}/{generated_filename}
```

The document ID is taken from the authorized server-side document record. The filename is generated by the backend with a random UUID-based name; the client-supplied filename is used only as sanitized metadata and for its extension. Clients cannot control the storage path.

## Upload

An upload requires:

1. An authenticated user with `documents.update`.
2. An active application profile.
3. Document-level access to the target document.
4. Server-side file validation.
5. A server-generated storage path.

The new object is uploaded before document metadata is updated. If the metadata update fails, the newly uploaded object is removed as best-effort cleanup and the failure is returned. The old object is retained until the metadata points to the new object.

## Download

A download requires authentication, `documents.read`, an active profile, and document-level authorization. Archived documents are blocked by the file endpoint and are reported as not found. After those checks, the backend retrieves the object from private Storage and returns the file response.

## Replacement

```text
new upload
    ↓
metadata update
    ↓
old object removal
```

If the new upload fails, metadata and the old object are unchanged. If the metadata update fails, the new object is removed on a best-effort basis and the old object remains authoritative. After a successful metadata update, removal of the old object is best effort; a cleanup failure is logged without exposing storage details.

## Validation

The configured limits are:

- Supported MIME types: `application/pdf`, `text/plain`, and `application/vnd.openxmlformats-officedocument.wordprocessingml.document`.
- Maximum size: `25 MiB` (`25 * 1024 * 1024` bytes).
- Filenames must be present, must not contain path separators, NUL bytes, `.` or `..`, or begin with a dot.
- Sanitized display filenames are limited to 150 characters and use a restricted ASCII-safe character set.
- PDF files must begin with `%PDF-`.
- DOCX files must begin with the ZIP signature `PK\x03\x04`.
- `text/plain` has no reliable binary signature and therefore has no signature check in the current implementation.

## Security

> Knowing a `storage_path` is not sufficient to access a document.

Every file operation still requires FastAPI authentication, RBAC, active-profile, and document-level checks. Storage RLS on `storage.objects` is defense in depth against direct access with non-service credentials; FastAPI remains the application authorization boundary. The bucket is private, and the service role is never exposed to clients.
